Objectif :
- Remplacer la base de données Supabase/PostgreSQL par MySQL/MariaDB.
- Conserver 100 % des données déjà présentes dans Supabase.
- Ne supprimer, vider ou modifier aucune donnée Supabase avant validation complète de la migration.
- Préparer le projet pour fonctionner avec MySQL en production, éventuellement sur Plesk.

IMPORTANT — RÈGLES DE SÉCURITÉ :
1. Ne supprime jamais la base Supabase.
2. Ne lance jamais de DROP DATABASE, TRUNCATE, DELETE global ou migration destructive.
3. Ne modifie pas le schéma Supabase sans créer une sauvegarde préalable.
4. Avant toute modification, inspecte le projet et explique-moi :

   - les données Supabase n'ont pas été exportées ;

   - les comptes et relations n'ont pas été contrôlés ;

6. Utilise les secrets et variables d'environnement de la plateforme. N'affiche jamais les mots de passe, tokens ou chaînes de connexion dans les logs ou dans tes réponses.

PHASE 3 — CONVERSION DU SCHÉMA VERS MYSQL :
Convertis le schéma PostgreSQL vers MySQL/MariaDB sans changer la signification des données.

Règles de conversion :
- PostgreSQL `serial`/`bigserial` → `AUTO_INCREMENT`.
- PostgreSQL `uuid` → conserver les UUID comme chaînes ou utiliser `CHAR(36)` selon le schéma existant.
- Ne remplace pas automatiquement les UUID par des nombres si cela casse les relations.
- PostgreSQL `boolean` → `BOOLEAN` ou `TINYINT(1)`, en conservant le comportement attendu.
- PostgreSQL `numeric`/`decimal` → `DECIMAL` avec une précision suffisante pour les montants.
- Ne convertis jamais les montants financiers en `FLOAT`.
- PostgreSQL `jsonb` → `JSON`.
- PostgreSQL `timestamp with time zone` → type MySQL approprié, en conservant les dates dans une convention UTC.
- PostgreSQL `text` → `TEXT` ou `LONGTEXT` selon la taille réelle.
- PostgreSQL enums → `ENUM` MySQL ou table de référence si cela est plus sûr.
- Conserve les valeurs NULL.
- Conserve les valeurs par défaut utiles.
- Recrée les clés primaires.
- Recrée les clés étrangères.
- Recrée les index uniques et index de recherche.
- Vérifie les noms réservés MySQL.
- Vérifie les différences de casse entre PostgreSQL et MySQL.
- Vérifie les colonnes JSON et les requêtes qui les utilisent.

Ne modifie pas les données uniquement pour rendre la migration plus facile. Si une conversion est ambiguë, arrête-toi et explique le problème.

PHASE 4 — MIGRATION DU CODE SERVEUR :
Remplace la connexion PostgreSQL/Supabase par MySQL/MariaDB avec le driver adapté, par exemple :
- `mysql2/promise`;
- `drizzle-orm/mysql2`;
- `drizzle-orm/mysql-core`.

Utilise une variable d'environnement comme :
`MYSQL_DATABASE_URL`

Conserve temporairement l'ancienne variable PostgreSQL uniquement si cela permet un rollback sûr, mais le code final doit utiliser explicitement MySQL.

Adapte les requêtes PostgreSQL incompatibles avec MySQL :

1. `.returning()`
MySQL ne supporte pas `.returning()` comme PostgreSQL.

Remplacer :
- INSERT + RETURNING → INSERT, récupérer `insertId`, puis SELECT de la ligne créée.
- UPDATE + RETURNING → UPDATE, puis SELECT si la réponse doit contenir la ligne.
- DELETE + RETURNING → DELETE, puis utiliser `affectedRows` ou SELECT avant suppression si nécessaire.

Avec Drizzle/MySQL :
- le résultat d'un INSERT est un tableau ;
- l'identifiant doit être lu avec `result[0].insertId` ;
- pour UPDATE/DELETE, le nombre de lignes doit être lu avec `result[0].affectedRows`.

Ne jamais utiliser `rowCount` PostgreSQL dans le code MySQL.

2. SQL brut
Convertir notamment :
- `::int` ;
- `::numeric` ;
- `::text` ;
- `::jsonb` ;
- `FILTER (WHERE ...)` ;
- `ON CONFLICT`;
- `RETURNING`;
- `ILIKE`;
- `ANY(...)`;
- `INTERVAL '24 hours'`;
- `metadata->>'field'`;
- les opérateurs JSON PostgreSQL ;
- les casts PostgreSQL.

Exemples :
- `count(*)::int` → `count(*)` ou `CAST(... AS SIGNED)`.
- `amount::numeric` → `CAST(amount AS DECIMAL(...))`.
- `count(*) FILTER (WHERE status = 'SUCCESS')`
  → `SUM(CASE WHEN status = 'SUCCESS' THEN 1 ELSE 0 END)`.
- `ON CONFLICT (...) DO UPDATE`
  → `ON DUPLICATE KEY UPDATE`.
- `metadata->>'paymentId'`
  → `JSON_UNQUOTE(JSON_EXTRACT(metadata, '$.paymentId'))`.
- `NOW() - INTERVAL '24 hours'`
  → `NOW() - INTERVAL 24 HOUR`.
- `ILIKE`
  → `LIKE`, avec une vérification de la casse et de la collation.
- `WHERE id = ANY($1::int[])`
  → `WHERE id IN (?)`, avec gestion explicite des tableaux vides.

Si le projet contient beaucoup de SQL brut avec des paramètres `$1`, `$2`, etc., crée si nécessaire une couche de compatibilité contrôlée qui convertit les paramètres PostgreSQL vers les paramètres `?` de MySQL. Teste cette couche avec :
- des paramètres dans un ordre différent ;
- des paramètres réutilisés ;
- des requêtes SELECT ;
- des requêtes INSERT ;
- des requêtes UPDATE ;
- des requêtes DELETE.
